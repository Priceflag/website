Test a price — waitlist

Standalone prototype for sections/pf-waitlist.js. The module builds every node it needs inside the mount, injects its own <style> once (refcounted) and returns a cleanup function. Exactly one global: window.initPfWaitlist.

The interaction. Two real inputs — the merchant's price and unit cost, defaulting to $48.00 / $19.00. Every keystroke re-runs the model and the forecast eases to its new value over 400ms. It shows the price Priceflag would test, the 90-day profit uplift, and always a low–high range: a point estimate on its own would be a lie about how much we know.

The model is the one the simulation section runs, so the two cannot disagree: orders(P,e) = 25.2·(P/P0)^e over 90 days, with elasticity as a band [-1.9, -0.9]. The band's centre picks the price to test — the profit curve peaks at P* = C·e/(1+e), capped at a ±12% move — and the band's ends, scored at that same price, give the two bounds. At the defaults that is $53.76, +$1,497, and a range from −$2.2k to +$5.4k: the low end is a real loss, and the section says so.

The email. There is no backend and the module does not pretend there is. A valid submit opens a mailto: to hello@priceflag.org prefilled with the address and the numbers on screen, says so in the confirmation, and leaves the same mailto on screen as a real link. Swap window.initPfWaitlist.T.SUBMIT for a real endpoint and the copy switches to the "you're on the list" wording on its own — the button below does exactly that.

Why the readout is measured, not eyeballed. This page can run with document.hidden === true, which starves requestAnimationFrame, ResizeObserver and IntersectionObserver alike. A screenshot proves nothing. The panel below reads the text the module actually wrote and the live SVG coordinates of the range bar, so "distinct frames" only climbs if something is really being redrawn. When rAF is dead the module detects it and sets values instantly instead of tweening — so the numbers are right on every keystroke even when the count never moves.
